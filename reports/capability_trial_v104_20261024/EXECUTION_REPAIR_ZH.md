# V104 推理前工程修复：随机种子与异常费用结算

用户提供的新共享分析末段指出两个具体问题。对本地实际运行代码核查后确认：Python `random` 未固定，而旧模型的图像补边会使用它；原守护在 `guard()` 抛出异常时，可能跳过当前 GPU 子进程的累计耗时与退出回执。

本次采纳这两项修复，自行核对与实现，没有依赖另一个会话未部署的修复包。共享分析所称 GPU 工作区缺失和 GitHub 403 属于那个会话；本会话已有服务器访问和成功推送记录，不把其阻塞移植到本会话。

1. 在 worker 准备任何输入前调用 `random.seed(0)`，与现有 Torch seed0 一起固定。模型、样本、问法、处理器规则和科学门槛不变。
2. 子进程成功创建后，在 `finally` 内回收并结算一次实际历时，保留退出回执；启动失败或已有日志阻止启动时不虚增 GPU 费用。
3. 下载已经开始，旧控制器不能靠替换磁盘文件获得已加载代码的修复。因此仅在核实尚无 GPU worker、累计 GPU 时间为零时，按 PID 与 start_ticks 停止旧守护，并由新守护接管同一个下载进程。保留原 `ONCE`、原始起点、截止时间、下载文件和全部旧回执；独立 `ADOPTION_ONCE` 禁止重复接管。已有下载不重启，已完成回答不重跑。接管后的超时仍可终止身份匹配的自有下载进程。

实际部署前执行了 CPU 模拟：正常结束、非零退出、守护中断、进程创建失败、已有日志、接管下载超时、接管身份不符，共7项通过。测试没有启动真实子进程、加载模型或调用 GPU。模拟中的 GPU 秒只是核验记账逻辑，不计为实验费用。测试夹具初次缺少 `STDOUT` 常量，第二次对不会实际改变 `/proc` 的模拟信号设置了过严次数断言；两次夹具失败与修正已私下保留，最终全部通过。

该修复只解决可复现性与成本记录，不构成模型或 TT 性能结果。接管身份、原始窗口与实际运行状态由私有部署回执记录。V104 继续遵守原协议，完成后回到 TT 主线，不追加 Base 搜索或重复数据筛选。
