# T5 同输入推理路径对照：64次生成的结果与限制

日期：2026-11-08。本轮为工程诊断，不是新CORE评测、作者T5表格复现或新方法实验。范围在输出前冻结，见 [PREREG.json](PREREG.json)。

## 主要发现

**在这32个固定输入上，切换到干净进程中的官方原生FP16入口，仍然得到32个No回答，与本地A路的完整生成tokens逐一相同。** 因此，本面板不支持“偏No只由本地FP32生成封装造成”的解释。它不证明全部322个任务或其他输入都等价，也不证明当前RGB渲染和提示就是M3Bench作者实际使用的配置。

**图像没有在整条计算链中被简单地忽略。** 同一患者前后图像在两个入口中都产生了不同的像素张量、视觉特征、projector输出、融合嵌入和首步logits；但所有二值回答仍为No。更准确的结论是“影像差异进入了计算，未在本面板形成有效的存在性答案区分”，而非“模型完全没读图”或“医学证据已被正确使用”。

另有一项必须记录的执行限制：诊断A路省略了原base.py进入循环前的一次fp32初始化调用，因此首个输入的预填充初始化顺序不完全复刻原路径。32个A回答仍全部复现历史tokens，但这不能补足数值路径等价证据。详见第4节；没有为此追加生成或覆盖原始记录。

## 1. 样本与执行

- 从322个既有任务中选择全部6个10、按原源顺序取前5个01和前5个11，共16个纵向任务、13个患者组、26张唯一影像；每个任务分别输入既往与随访图，得到32个输入。
- 不依据Base资格或方法结果挑选，不把此分层面板当成独立测试集。已知的CT比较来源疑点仍保留，仅用于工程对照，不用于临床标签准确率。
- A和B分别在新进程中加载原始checkpoint，均使用已核实的official_native loader；两者加载后都没有已有forward hooks、没有编辑器参数或路由。A使用现有FP16准备／FP32生成封装；B使用官方prompt与原生model.generate、FP16模型。
- 同一份已渲染RGB和原问题，固定逐图预处理随机种子，贪心生成、最多1024个新tokens。没有重新做16位图像转换、没有下载模型、没有生成权重副本。
- 实际完成A32+B32，共64次完整生成；0训练更新、0Judge、0历史UNKNOWN重试、0资格或标签变更。

两个GPU进程均正常退出，独立guard也已退出。远程新增占用约0.903GB，低于3GB限额；整个过程在原两小时硬时钟内结束。既有T5修正版继续运行，最后核验时GRACE仍正常推进；本轮没有停止、重启或重配它。

## 2. 两条入口的直接比较

| 观测 | 结果 |
|---|---:|
| prompt文字与token IDs一致 | 32/32 |
| 实际pixel_values精确一致 | 32/32 |
| 融合后的backbone attention mask一致 | 32/32 |
| 第一层position IDs一致 | 32/32 |
| 原始生成tokens、完整回答均一致 | 32/32 |
| A生成tokens与历史Base一致 | 32/32 |
| A / B回答以No开头 | 32/32 / 32/32 |
| A / B正常EOS | 32/32 / 32/32 |
| 截断／达到上限 | 0 / 0 |
| 首步logit argmax相同 | 32/32 |

原始attention-mask调用参数存在表示差异：A显式传入，B走原生入口缺省；实际进入backbone的mask和position IDs一致。第一decoder层接口未显式提供attention mask，双方都为None，不能把这个“双方缺省”当成独立的数值验证。

内部数值并非逐位等价：视觉特征、projector输出和融合嵌入仅1/32精确相同；视觉特征最大相对L2差约2.79%，projector约3.29%；首步logit最大绝对差约0.0203、KL最大约1.98e-5。不同精度、后端状态与入口混在一起，不能把所有差异归因于FP32 decoder，也没有按结果设置“足够接近”的容差。**本轮明确证明的是输入控制和输出一致，不是完整数值链等价。**

这不支持“图像完全没有传进模型”的简单解释；同时，首步概率受到图像影响，并不证明其方向与真实病征对应。参见 [PAIRED_SUMMARY.json](PAIRED_SUMMARY.json)。

## 4. 初始化顺序偏差与源代码版本

实际64次生成使用的执行源为提交 `cebe33099cec20954e6a20dde7a32010bca2f58a`，远程原始worker与输出未被替换。复核发现：

1. 原始T5 base.py在加载后、进入输入循环前调用fp32(runtime)，既转换参数精度，也设置math SDP等后端状态。
2. 本轮A runner省略了这次循环前调用，但每个输入准备后都会调用。故只有首个输入的准备阶段可能处在不同的初始后端状态；其后的准备阶段已继承该调用设置。首次准备时的具体后端flag未单独保存，不能把影响大小事后当成已测量事实。
3. 跨A/B视觉特征恰好只有首个输入精确相同，其余31个不同。这与初始化顺序／后端差异有关联线索，尚非独立因果证明；尤其不能归因成原始T5代码也漏了初始化，原始代码有该调用。
4. 已修正仓库runner，恢复循环前初始化，供以后复用。**本轮没有重跑首个输入、没有增加第65次生成，也没有将修正后的代码冒充已经执行的源码。** 原始64次结果与偏差记录均保留。

因此，关于A是否完整复刻本地数值路径的主张必须受限。官方B的32个生成来自独立原生进程，没有该A初始化顺序问题；其“在本面板也全部回答No”的观测仍成立。

另有一次远程启动包装脚本的换行转义错误，发生于远程Python解析阶段，尚无远程执行或模型调用，已修复并保留收据。没有重置原时钟。执行审计见 [EXECUTION_AUDIT.json](EXECUTION_AUDIT.json)。

## 5. 这轮能排除什么，仍缺什么

可以在本面板内排除：只要换回官方原生FP16入口，偏No就会消失；也没有看到图像张量被替换成完全相同输入。清洁进程重载复现历史回答，还削弱了“先前编辑器残留才导致这些Base回答”的解释。

仍不能排除：共享的RGB渲染、问题模板、具体checkpoint／视觉塔配置或骨干本身在这些输入上的偏差。两路共享这些条件，因此不会自动揭示这些共同因素的问题。16任务也不是全322任务的性能代表。

作者的Temporality分母、实际队列与执行器仍未获得，故本轮不能完整解释作者0.42–0.66与本地高分的差距。应保留[分母对账](../med_t5_denominator_audit_v1_20261108/REPORT_ZH.md)与[源标签审查](../med_t5_change_audit_v1_20261108/REPORT_ZH.md)的结论；不据此修改MDU、重建资格或声称作者数据有问题，也不立即扩成prompt／窗宽／精度搜索。
