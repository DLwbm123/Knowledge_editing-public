# Protocol metadata erratum, 2026-10-02

During E23 preparation, review found legacy descriptive fields retained in the nested PROTOCOL.json objects inherited by E20-E22: top-level method/max_steps/target_rule/rounding/max_generation_tokens and some historical control descriptions could contradict the current variant sections and PROTOCOL.md. In particular the stale fields refer to three steps, mean-logprob gain and stochastic rounding, whereas actual E20-E22 scientific runs used six steps, native-prefix minimum margin+0.01, nearest BF16 writes and64-token full generation. E22 used W_FT, E20/E21 W_FUNCTIONAL_QP. Some nested control.reference labels were also shifted by preparation-script string replacement. These are documentation defects; no frozen protocol or result is overwritten.

EXECUTED_CONFIG_AUDIT.json publishes the exact relevant nonprivate fields read from the original bound execution configurations. Runtime case receipts independently identify branches, dtype, rounding, target objective, threshold, prefix path and realized steps. The driver reads these actual top-level configuration fields, not the stale nested descriptive values. Current PROTOCOL.md and variant-specific settings described the intended six-step/native-prefix experiments before launch. Their frozen source/config bindings and costs remain unchanged.

This erratum does not retroactively change an experiment, threshold, success criterion or result. It makes the conflicting metadata explicit rather than silently rewriting frozen evidence. E23 uses a complete standalone protocol matched to actual configuration with an explicit consistency check, and newly bound protocol/config receipts before launch. Earlier inherited protocol JSON should be interpreted alongside its dated current-variant PROTOCOL.md, bound execution config and runtime receipts; legacy fields alone are not a reliable reconstruction recipe.
